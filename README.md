# internal-project-management-tools
KoinBX Backlog Tracker is an internal web app for planning and tracking team work. It organizes tasks into two-week sprints and PODs, with an owner, lead and assignees on each task. My Task and My Sprint give each person their own view and hour logging, while admins manage users. Built with Next.js, React and TypeScript, with dark themes.


## Shared storage: one set of data for every computer

The app runs as a Node server (`npm run dev`, or `npm run build && npm start`). The data lives on the machine that runs it, so every computer and browser that opens the app sees the same accounts, tasks, Tickets, sprints, comments, attachments, notifications and history. The page talks to the server through `POST /api/rpc` (the same routes and rules as before, now in `src/lib/localApi`, answered on the server); there is no other database to install.

- **Where the data is.** In the folder named by `KOINBX_DATA_DIR`, or `.data` in the app's folder (it is in `.gitignore`): `db.json` (all records, written whole and atomically after every change), `blobs/<id>` (one file per attached image) and `sessions.json` (only hashes of sign-in tokens). Back this folder up. Requests are handled one at a time, so two people saving together never overwrite each other. It is built for one server process; for several, move the store in `src/lib/server/store.ts` to a real database.
- **Sign-in and sessions.** Sign-in sets an httpOnly, SameSite=Lax cookie (Secure over https) holding a random token; the server keeps only its hash, and a session lasts a week of use. Sign out ends it on the server, and changing a password signs the person out everywhere else. The API only answers requests that carry the app's own header, and every role and permission check now runs on the server.
- **Other computers' changes.** Each page asks the server every few seconds whether the data changed and re-reads what it shows, so new tasks, comments and notifications from other people appear without a reload.
- **Moving the data you already had in a browser.** Open the app in the browser (at the same address) that holds the old data, while the server is still empty: the first-run screen offers **Import existing data**. It moves accounts, tasks, Tickets, comments, notifications, history and images to the server once; the server refuses it as soon as any user exists, so it cannot overwrite or duplicate anything. The old data in that browser is not deleted. Everyone then signs in with the same passwords.

```bash
npm install
npm run dev      # or: npm run build && npm start
```

- **Starts empty.** There is no sample data. The first visit asks for the first account (a Super Admin); that account then adds everyone else, and tasks, sprints, owners, PODs and work logs are entered or imported from Excel.
- **Persistence.** Data is kept on the server (see above): it survives refreshes, restarts and clearing a browser's site data, and every computer sees the same latest data. A connection problem shows an error message instead of pretending the app is new.
- **Ticket images.** Create Ticket (and the Ticket window) takes one or more JPG, JPEG, PNG or WebP images of any original size, at most 10 per Ticket. Each image is optimized in the browser to about 20 KB as it is chosen (WebP, or JPEG where the browser cannot encode WebP): quality is lowered first and the dimensions are kept; only if that is not enough are they reduced slightly (to 85%), and if about 20 KB still cannot be reached without hurting clarity the image is kept at the smallest size that still looks clear, so a very detailed picture can stay larger. An image already under 20 KB is stored untouched. This is lossy compression (never lossless): the picker and the Ticket show the original and optimized sizes and dimensions. The type is checked from the file's own bytes, so a renamed document is refused with a clear message. The optimized Blob is stored in the browser's IndexedDB together with its attachment id, Ticket id, original filename, type, original and compressed size and upload date; the main data keeps only the details, never the image as text, and temporary `blob:` preview addresses are never saved and are released when an image is replaced, removed or the form closes. In development (`npm run dev`) the browser console logs each optimization under `[Ticket Image Optimization]`. The Ticket window shows the images and opens each larger, and the people who may edit the Ticket can add or remove images. Images are not part of the backup file; a restore on the same browser keeps the ones whose Ticket is still there.
- **QA creating a Ticket.** When a QA team member (Team QA) creates a Ticket under a task, they are added to the task's Assigned Users (everyone already assigned stays), and the change is written to the task's history. When it is the task's first Ticket and the task is Ready for QA, the task also moves to Testing, the move is recorded in its history, and a "Testing started." comment is added to it. Each part acts only if it still has something to change, so a retried request does not repeat the status change, the comment or the assignment (a second Ticket with the same title is refused). The Ticket's own assignee is only what was chosen in the form. Nobody else's creating a Ticket changes the task. The data layer does it, from the signed-in user.
- **My Task highlight and Ticket assignment notices.** A My Task row is tinted (with an accent bar) when the signed-in user is among the task's Assigned Users, matched by user id, so it survives refresh and navigation; a QA member creating a Ticket still becomes the task's assignee. A "Ticket assigned" notification is created only when a Ticket is actually assigned to someone (the assignee gets it, including when they assign it to themselves); creating a Ticket under a task, or being assigned the parent task, never notifies on its own, and a Ticket and its parent task are assigned separately. The bell shows how many open Tickets are assigned to the signed-in user, updates at once, and clicking a notice opens that Ticket.
- **Main Task page layouts and Ticket teams.** The Main Task page has a List / Board switch (kept in the address; it opens in List). List View: the search and filters across the full width on top, then the Tickets as an expandable list on the left and the task's details and comments on the right, in equal halves. Board View: the status board on top (drag a card to another column; the move asks for its usual comment and respects who may change the status), the task's details underneath. A Ticket opens in its window over either layout and stays marked after it closes. Search and the filters (Created By, Assigned To, Status, Priority) are shared by both layouts; teams are used by the Group by choice. A Ticket records who created it (their id and name) and their team as it was at that moment, taken from the signed-in profile; its Assigned Team is the assignee's current team, so it follows a reassignment and is never assumed to be the creator's team. Teams are names in this app (there is no team id), so a team's id for filtering is its cleaned, lower-case name. Main Task comments show the author's name and team and the time, can be edited by their author (marked "edited") and deleted by the author or an admin, and are separate from Ticket comments.
- **QA Workspace.** One page (`/qa-workspace`; the old `/ready-for-qa` links redirect to it) for every task handed to QA, for the QA team, the Super Admin and enabled Admins, with the same three statuses for everyone: Ready for QA, Testing and Done. A **List / Board** switch (kept in the address; List by default) shows the same tasks two ways, under one search and one set of Status / Priority / Team / Assignee filters (and sort), which are kept while the tab is open and when switching. **List**: a table with task id, task, status, priority, assignee, team and Ticket count, sortable by clicking a heading (ascending, descending, default). **Board**: a column per status with its count and a card per task (id, title, priority, assignee, team, Ticket count). QA members and admins drag a card to the next column (Ready for QA → Testing → Done, one step at a time; each move asks for the usual status comment, changes only that task and shows at once in both views; Done needs all the task's Tickets Done). **Reopen** on a Done task puts it back to the status it had. Clicking a row or card opens the task's full page (Tickets, comments, images, history; Back to QA Workspace returns, with the task still marked), where Open for testing and the status change (once all Tickets are Done) are also available. Moves are not available by keyboard on the board; use the task page for that.
- **Chat-style comments.** Main Task and Ticket comments (each its own conversation) are laid out as a chat: initials avatars (people have no profile pictures here), name, team and time on every message, your own messages on the right, the conversation scrolled to the latest message with the message box under it, and a "New messages" line for what arrived since you last looked. Enter sends, Shift + Enter is a new line. Typing `@` lists the people (avatar, name, team; search by typing, arrows + Enter or a click pick one); several can be mentioned, mentions are highlighted, and each mentioned person gets one notification (they are not also sent the ordinary comment notice; an edit notifies only people newly mentioned). The paperclip (or paste) adds up to 5 images per message, previewed in the box with Replace and Remove, optimized to about 20 KB like Ticket images and stored as Blobs in IndexedDB (previews are temporary `blob:` addresses only); sent images show in the message and open larger. Authors edit or delete their own messages (admins may delete). A mention notification opens the task, and its Ticket window for a Ticket comment, scrolled to and highlighting that message.
- **Ticket page.** A Ticket opens as its own full page (there is no window over the task), laid out like ClickUp's task view: the main column has the Ticket id and its task, the title with Edit (then Save / Cancel) and Reopen, a grid of properties (status, assignee, assigned team, priority, due date when set, creator and their team, dates, parent task, sprint), the description and the images; the column beside it holds the Comments (chat-style, with @mentions and images) and the Activity history (status changes, assignments, reopen details). The assignee and priority change at once, the status asks for its comment, and the title and description wait for Save; what is typed stays while switching between Comments and Activity. Back returns to the task with the Ticket still marked, and the task page keeps its search and filters for that tab. A card dragged to another board column opens the Ticket page with that status waiting for its comment. There are no custom fields in this app, so none are shown.
- **My Task views.** My Task opens in Board view and has a List / Board switch (kept in the address); opening a task starts in its List View. List is the table; Board shows the same tasks of the open tab (My Tasks, My Lead Tasks, Unassigned) in columns To Do (with Blocked and On hold badges), In Progress, Ready for QA, Testing and Done, each with its count and a card per task (id, title, priority, type, sprint, ETAs, Ready for QA date). Tasks assigned to you keep the tint and accent edge, and a card opens the task page like a row does. The board is view-only: statuses are still changed on the task page, where the comment and the status rules apply.
- **Colours.** The theme is a calm slate-blue palette: cool neutral surfaces and borders, the logo blue slightly deeper for text and controls (about 6:1 on white), the logo cyan kept in dark mode, and softer tone-on-tone status and priority badges with a hairline ring (Open blue, In progress indigo, Ready for QA teal, Testing violet, Blocked red, On hold amber, Done emerald; Critical red, High orange, Medium amber, Low slate). The text colours were checked for at least 4.5:1 contrast. Primary buttons are solid accent everywhere (the gradient is only on the sign-in screens), every disabled control has the same dimming, and the overview chart colours match the status badges. The tokens are at the top of `src/styles/globals.css` and the badge colours in `src/components/ui/Badge.tsx`, so the palette can be changed in those two places.
- **Design system.** One corner-radius scale (controls 8px, cards and inputs 10px, panels and modals 12px), form fields that focus in the accent colour like every other control, and one filter toolbar (search, the app's own dropdowns, Clear) on every page that filters: All items, Team Members, Owners & sprints, QA Workspace, My Task's Tickets and a task's Tickets. The stat tiles use the same status hues as the badges, and All items fits its eight tiles in one row on a wide screen.
- **Tickets before QA.** While a task is To Do or In Progress (and Blocked or On hold, which sit in To Do) its Tickets section is not shown anywhere (task page, task panel, Edit drawer); the Tickets themselves are untouched and show again once the task is Ready for QA, Testing or Done. In those statuses the task page is two columns: Task details on the left and Comments on the right, stacked with the details first on a small screen, and there is no List / Board choice.
- **Deleting hidden tasks.** In All items > Hidden an admin can use **Remove all hidden**, which (after a confirmation) permanently deletes every hidden task together with its child Tickets and their comments and images; hidden tasks in a closed sprint stay and are counted in the message. Deleting a single task now also deletes its child Tickets (the confirmation says how many), where it used to be refused; a task with child tasks of another kind is still refused until they are dealt with.
- **Opening a notification.** Clicking a notification (in the bell's panel, or on a task card's bell) opens the task, Bug or Ticket it is about straight away, found by its id so it works from any page (the QA team and admins land in the QA Workspace pages, everyone else in My Task), at its comment when it is about one. Only that click marks it read; just displaying the list or opening the panel never does. It leaves the Unread list and the counts at once and stays in All as history. A task card's bell opens the latest unread notice about the task or its Tickets, one at a time. The Mark read and Mark all as read buttons remain as explicit actions. A notice identical to one the person still has unread (same kind, item, text, change and comment) is not added again.
- **Developer ETA.** The task's Lead and its Assigned Users (not only the Lead) can set the Developer ETA (Estimated Time of Arrival) while the task is in development (not with QA); the Assigned User's panel has the field next to the status, and the data layer accepts it from them. Changing the assignees and the status of a task by a non-Lead is still refused.
- **Status notes are comments.** The comment typed with a status change (every status change asks for one; a reopen's reason is optional) is recorded twice by the data layer: in the task's or Ticket's history, as before, and as a comment from the person who made the change, so it also shows in the conversation (the Main Task's for a task, the Ticket's for a Ticket) and the conversation refreshes at once. It does not notify anyone a second time.
- **Group Tickets by team.** A task's Tickets section has a **Group by** choice next to the filters: No grouping, Assigned team (the team of the assignee) or Created by team. Grouped, the Tickets are shown in one section per team with its count, teams in name order and "No team" last, in the List, Board and table layouts alike. Grouping works with the search and filters, and is kept for that task while the tab is open.
- **Where Tickets and comments show.** A task's Tickets are managed on its Main Task page (List or Board View, with the filters above). The Edit drawer (opened from the lists) and the task side panel do not repeat the Tickets or the comments: they show the details, hours and history. A task's comments are on its Main Task page.
- **Reopen.** A completed task shows **Reopen** on the Done page and on its task page; a completed Ticket shows it in its window (its status field is locked while it is Done). The reason is optional. A task goes back to the status it had just before it was completed (not To Do) and its Tickets stay as they are; a Ticket goes to the status chosen in **Reopen to [Status]** (To Do, In progress or Testing) and its task is left alone. Every reopen adds one permanent history entry ("Ticket Reopened" or "Task Reopened": reopened by, date and time, previous status, reopened status, reason) and earlier ones are never replaced; the Ticket window's Details also shows the latest reopen. The id, title, Ticket links, comments, images and history are kept, with the completion date shown as "Last completed" and the day as "Reopened". The admins, QA and the task's Lead can reopen, with the same choices for all of them.
- **Backup & restore.** The Super Admin can **Export backup** (a JSON file of everything, with sign-in hashes but no passwords) and **Restore from file** in Settings. A restore shows what the file holds, asks to confirm, refuses a file that is not a valid backup, and replaces all the shared data on the server for everyone. It guards against losing the data folder and can move the data to another server.
- **Sign-in.** Email plus password, for every role. Passwords are stored only as salted PBKDF2-SHA256 hashes (hashed on the server).
- **Notifications.** Created when a task is assigned, changes status or sprint, or is commented on, and kept on the server; every computer sees them within seconds.
- **Task hierarchy.** Backlog task, then Bug, then Ticket: a Bug may sit under a Feature/Enhancement/Task/Tech Debt, and a Ticket sits under a task or a Bug. A task with children cannot be deleted. Hours roll up to the parent on the task details.
- **Ready for QA.** Every task whose status is Ready for QA is listed there, whoever it is assigned to, for the QA team (people whose Team is QA or Testing), the Super Admin and enabled Admins. Each task is the original record under its own name, with its Tickets nested underneath (TKT-001, TKT-002, ... with title, status, priority and assignee); no Bug is created. Click a task to open its full page (`/ready-for-qa/task?id=…`) with its details, status, a Tickets board, **Create Ticket**, history and comments; click a Ticket to open its own full page (`/ready-for-qa/ticket?id=…`) to edit its title, description, priority and assignee, change its status and read its history and comments. Back returns to the task, then to Ready for QA. Every Ticket is linked to its task's id and the same title can't be added twice under one task. When every Ticket of a task is Done, the QA team (not the admins) gets a status control at the top of that task on the Ready for QA list (Testing, Done or back to In progress, with the comment every status change carries). QA marks the task Done when testing is complete; it then leaves the section and keeps its Tickets, comments, hours and history.
- **My Task.** The page lists Backlog tasks only (ID, name, type, priority, status, sprint, ETAs); a Ticket is never a row of its own, but the task that holds a Ticket assigned to you is listed so you can reach it. Clicking a task opens its own full page (`/my-task/task?id=…`): its header and all its Tickets as a board (To Do, In Progress, Ready for QA, Testing, Done, each with its count); the other details (status panel, hours, history, comments) are on the Ready for QA task page instead. Create Ticket is on that page for the task's Lead and Assigned Users, QA (while the task is with QA) and admins. Clicking a Ticket opens its page (`/my-task/ticket?id=…`) to edit it and change its status; Back returns step by step.
- **Status flow.** To Do, In progress, Ready for QA, Testing, Blocked, On hold, Done. Only QA and admins take something into Testing. Only a Super Admin or an enabled Admin can mark a task Done; others hand work on with Ready for QA.

### Security

Roles (Super Admin, Admin enabled/disabled, User) are checked on the server for every request, against the account the session cookie belongs to; the screens only mirror what the server allows. Passwords are stored as salted PBKDF2-SHA256 hashes; the data folder holds those hashes and everything else, so protect it like any private data. Use https in front of the app for anything beyond a trusted office network: over plain http the session cookie is not marked Secure.

- **Form sizes.** One rule: a large form (Create / Edit backlog, task details) is a tall, wide card centred over the blurred page and expandable; a small one (a name, a few fields, a confirmation, read-only details) is a card 28rem wide as tall as its content, centred the same way, and the small dialogs (Reopen, status, remove hidden, password notice) are the same 28rem; the new-Ticket form in a task's comments is a panel anchored at the top of that section. Small forms grow with validation messages and scroll only past the screen.
